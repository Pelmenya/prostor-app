# Мультиплатформенная стратегия PROSTOR

> **Статус:** Проектирование
> **Дата:** 12.03.2026
> **Цель:** Сделать CRM PROSTOR независимой от конкретного мессенджера

---

## Зачем

Сейчас PROSTOR работает **только** как Telegram Mini App. Это создаёт риски:

- **Блокировка Telegram в РФ** — потеря 100% пользователей за один день
- **Политика платформы** — Telegram может изменить правила, ограничить функциональность или забанить бота
- **Ограниченная аудитория** — не все клиенты и мастера пользуются Telegram
- **Зависимость от Telegram Payments** — единственный канал приёма платежей через мессенджер

**Цель:** один продукт — несколько точек входа. Клиент работает там, где ему удобно.

## Целевые платформы

| Платформа | Приоритет | Статус | Зачем |
|-----------|-----------|--------|-------|
| **Web (standalone)** | 1 — Высший | Проектирование | Независимость, SEO, desktop для мастеров и кураторов |
| **MAX Messenger** | 2 — Высокий | Исследование завершено | Российский мессенджер, замена при блокировке TG, SDK почти идентичен |
| **Telegram** | — | Продакшн | Текущая платформа, поддерживаем пока работает |
| **VK Mini Apps** | 3 — Средний | Будущее | Дополнительная аудитория |

### Почему Web первый, а не MAX

В предыдущем исследовании (декабрь 2025) рекомендовался MAX — SDK похож на Telegram, быстрая миграция. Но:

- **Web даёт полную независимость** — не зависим ни от какого мессенджера
- **Web = основа для всех платформ** — аутентификация, платежи, UI покрывают и мобильное PWA
- **MAX может повторить судьбу Telegram** — привязка к ещё одному мессенджеру не решает проблему
- **Мастерам нужен desktop** — заказы, маршруты, расписание удобнее на большом экране
- **SEO и органический трафик** — мессенджеры этого не дают

MAX делаем вторым — адаптер поверх готовой архитектуры.

### Принципы

1. **Backend платформо-независимый.** Один API для всех клиентов. Тип платформы определяется по заголовку авторизации.
2. **Frontend — Adapter Pattern.** Бизнес-логика, компоненты, стили — общие. Платформо-зависимый код изолирован в адаптерах.
3. **Один пользователь = один аккаунт.** Связь через номер телефона. Вход из Telegram, MAX и Web — одни и те же заказы, объекты, корзина.

## Этапы реализации

### Этап 0: Подготовка бэкенда (2-3 недели) — БЛОКЕР

Без этого невозможно подключить ни одну новую платформу.

- Миграция User.id с Telegram bigint на UUID
- Таблица UserIdentity (platform + externalId)
- Рефакторинг AuthService под мульти-аутентификацию
- Обновить deleteUser (GDPR) для новой структуры

### Этап 1: Web MVP (4-6 недель)

Минимально рабочая веб-версия для клиентов: каталог, корзина, заказ, оплата, профиль.

### Этап 2: MAX (2-3 недели)

Адаптер поверх готовой архитектуры. SDK почти идентичен Telegram.

### Этап 3: Полный Web (4-6 недель)

Desktop UI для мастеров/кураторов, карта, чат, PWA, SEO.

## Риски

| Риск | Влияние | Митигация |
|------|---------|-----------|
| Миграция User.id сломает прод | Критическое | Поэтапно, backup, тест на копии БД |

| TG заблокируют до готовности Web | Высокое | Этап 0 начать немедленно |
