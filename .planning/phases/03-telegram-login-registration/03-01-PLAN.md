<objective>
Wire the Telegram entry point that Phase 2 shipped as a disabled placeholder into a working end-to-end login (TG-01), and build the reusable OIDC + sessionStorage foundation the registration slice (Plan 02) and Phase 4 linking will consume. After this plan a real user with an existing Telegram-linked account can click «Войти через Telegram» and land in the personal cabinet; a brand-new Telegram profile is detected and routed to /telegram-register with its one-time registrationToken safely stored.

Purpose: This is the first genuinely new integration surface in the milestone — no prior OIDC/popup code exists. Getting the transport (nonce → popup → id_token → exchange) and the sessionStorage lifecycle right here keeps Plan 02 and Phase 4 as thin consumers, not rewrites.
Output: Three new API functions, a reusable `useTelegramOidc` hook, a `telegram-registration` sessionStorage lifecycle module, `telegramRegisterSchema`, and a fully-wired 5-state Telegram button on the login page.
</objective>

## Phase Goal (MVP user story)

**As a** user, **I want to** authenticate or register entirely through Telegram from the auth screen built in Phase 2, **so that** new accounts are detected correctly and email conflicts are handled gracefully instead of creating duplicate accounts.

This plan delivers the existing-user login half of that story (TG-01) plus the shared machinery the rest of the phase stands on.

<threat_model>

## Trust Boundaries

| Boundary                              | Description                                                                                          |
| ------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| browser → Telegram widget (external)  | User approves login in the Telegram-hosted popup; app receives a signed id_token it does not control |
| browser → backend (/auth/telegram/\*) | Untrusted id_token relayed to the backend, which is the sole verifier                                |
| sessionStorage → app                  | registrationToken/profile persisted client-side across the /telegram-register navigation             |

## STRIDE Threat Register

| Threat ID | Category            | Component                               | Severity | Disposition | Mitigation Plan                                                                                                                                                                                                                                                |
| --------- | ------------------- | --------------------------------------- | -------- | ----------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- |
| T-03-01   | Spoofing            | id_token replay                         | high     | mitigate    | Server-issued nonce from POST /auth/telegram/nonce is passed into `Telegram.Login.auth({ nonce })` and cross-checked backend-side against the issued nonce — the entire purpose of the nonce round trip. Frontend must always fetch a fresh nonce per attempt. |
| T-03-03   | Tampering/Elevation | id_token client-side trust              | high     | mitigate    | Frontend treats id_token as an opaque bearer value — never decoded, never trusted for any authorization/branching decision; only the backend verifies signature/iss/aud/exp/nonce. Enforced in use-telegram-oidc.ts + login-page.tsx (no jwt-decode).          |
| T-03-02   | Spoofing/Tampering  | registrationToken reuse/guess           | medium   | mitigate    | One-time-use + 10-min TTL enforced authoritatively server-side; client-side TTL check in telegram-registration.ts is UX-only. sessionStorage-only (never localStorage, never URL query).                                                                       |
| T-03-06   | Denial of Service   | COOP header breaks popup                | medium   | accept      | next.config.ts sets no headers() today (verified). Documented in-code that COOP: same-origin must never apply to /login                                                                                                                                        | /telegram-register; flagged for any future security-headers phase. No action needed now. |
| T-03-SC   | Tampering           | third-party script (telegram-widget.js) | low      | accept      | No npm packages installed this phase (package legitimacy N/A). The widget is Telegram's own hosted script loaded via next/script; script version verified live at execution (Pitfall 3).                                                                       |
