# Phase 3 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Mission of this phase (per ROADMAP.md/PROJECT.md):** wire up the Telegram entry point that Phase 2 shipped as a disabled placeholder (`login-page.tsx`), add the one genuinely new surface (Telegram registration-completion form), and design the two failure/edge states that don't exist anywhere else in the app yet: a mid-flow "session expired, restart" state (TG-03) and an email-conflict redirect (TG-04). This is a **continuation** of Phase 2's auth screen shell — no new design system, no new spacing/typography/color tokens. Every token below is carried over verbatim from `02-UI-SPEC.md` (Phase 2, approved) and re-declared here only so this file is self-contained for the checker/executor.

## Typography

Unchanged from Phase 2 — reused verbatim, no new sizes or weights introduced:

| Role                                                 | Size                                       | Weight         | Line Height |
| ---------------------------------------------------- | ------------------------------------------ | -------------- | ----------- |
| Micro (field error / help text / popup-blocked hint) | 12px (`text-xs`)                           | 400 (regular)  | 1.5         |
| Body (inputs, labels, footer links, alert text)      | 14px (`text-sm`)                           | 400 (regular)  | 1.5         |
| Button / interactive label                           | 16px (`text-base`, DaisyUI `.btn` default) | 600 (semibold) | 1.2         |
| Heading (`card-title`)                               | 24px (`text-2xl`)                          | 600 (semibold) | 1.2         |

`gradient-text` utility is the only heading treatment — the new completion page's `<h1 className="card-title text-2xl gradient-text">` must reuse it verbatim (e.g. "Завершите регистрацию"), same as Login/Register.

## Component Inventory — New Work This Phase

### 1. Telegram button on `login-page.tsx` — disabled → wired

Existing markup (Phase 2, `login-page.tsx:95-103`) is the locked visual baseline:

```tsx
<button
    type="button"
    className="btn btn-outline btn-primary w-full gap-2"
    disabled={/* was: always true — now: only true during in-flight states */}
    onClick={/* new: starts nonce → OIDC → exchange flow */}
>
    <TelegramIcon className="size-5" />
    {/* label swaps per state — see Copywriting Contract */}
</button>
```

State machine (visual only — technical transport for planner/RESEARCH to decide):

1. **idle** — enabled, icon + "Войти через Telegram", no `title` attribute (remove the Phase 2 placeholder tooltip).
2. **nonce-loading** — `disabled`, spinner + "Открываем Telegram…".
3. **awaiting-popup** — `disabled`, spinner + "Ждём подтверждения в Telegram…" (covers the window between popup open and the user completing/cancelling it in Telegram).
4. **exchanging** — `disabled`, spinner + "Входим…" (nonce/id_token → `POST /auth/telegram/login` round trip).
5. **error** — button returns to **idle**, an `alert-error` (see Copywriting) appears in the same slot the existing `serverError` alert uses (above the divider, matching the email-login error placement for visual consistency between the two auth methods on the same card).

Do not disable the email login form or its submit button while the Telegram button is in a loading state — the two entry points are independent; a user should be able to abandon the Telegram popup and use email login without a page reload.

### 2. Telegram registration-completion form (TG-02) — new page

New route: `/telegram-register` (flat top-level, matching the existing flat naming of `/verify-email`, `/reset-password`, `/forgot-password` rather than nesting under `/register` — consistent sibling, not a variant of the email form). New view: `src/views/auth/ui/telegram-register-page.tsx`, thin `page.tsx` wrapper at `src/app/(web)/telegram-register/page.tsx`.

Layout — same card shell as `register-page.tsx`, with one addition (avatar) and one removal (no password field):

```
<div className="card bg-base-200 shadow-xl w-full max-w-md">
  <div className="card-body">
    <h1 className="card-title text-2xl gradient-text">Завершите регистрацию</h1>
    <p className="text-sm text-base-content/60">Мы получили ваши данные из Telegram — осталось указать почту и телефон</p>

    {/* NEW — avatar, size-20, centered, gap-6 (lg token) below subheading */}
    <div className="flex justify-center mt-6">
      <div className={`avatar ${!profile.photo_url ? 'avatar-placeholder' : ''}`}>
        <div className={`relative size-20 rounded-full overflow-hidden ${!profile.photo_url ? 'bg-primary/10 text-primary' : ''}`}>
          {profile.photo_url
            ? <Image src={profile.photo_url} alt={fullName} fill className="object-cover" />
            : <span className="text-xl font-semibold">{initials}</span>}
        </div>
      </div>
    </div>

    <form className="flex flex-col gap-4 mt-4">
      {/* Имя, Фамилия — prefilled from Telegram profile, editable, same FormField+input pattern as register-page.tsx */}
      {/* Email — empty, required, same validation as register-page.tsx (trim/lowercase/email format) */}
      {/* Телефон — empty, required, same Controller+mask pattern as register-page.tsx (+7 999 999-99-99) */}
      {/* ConsentCheckboxes — reuse the exact component from register-page.tsx verbatim (same 2 checkboxes, same copy, same links) — extract to shared location if planner deems it, but do not restyle */}
      {/* NO password field */}
      <button type="submit" className="btn btn-primary w-full">Завершить регистрацию</button>
    </form>

    <p className="text-center text-sm mt-4">
      Это не вы? <Link href="/login" className="link link-primary">Войти другим способом</Link>
    </p>
  </div>
</div>
```

Reuse rules:

- `Image` from `next/image` for the Telegram `photo_url` — `next.config.ts` already whitelists `**.telegram.org` and `t.me`/`**.t.me` remote patterns (confirmed present, no config change needed).
- Avatar fallback (`avatar-placeholder` + initials): identical pattern to `curator-master-card.tsx:32-41`, just `size-20` instead of `size-10`, and `text-xl` instead of `text-sm` for the initials glyph (proportional scale-up, not a new token).
- `formatUserInitials` from `@/shared/lib` — reuse verbatim, do not reimplement.
- `ConsentCheckboxes` — the two checkboxes in `register-page.tsx` are currently a private (unexported) function inside that file. This phase's planner should either (a) extract it to a shared location the two forms both import, or (b) duplicate it verbatim into the new file if extraction is out of scope — **either is acceptable to this design contract**, but the rendered markup/copy/spacing must be pixel-identical to `register-page.tsx`'s version (same `flex flex-col gap-3`, same `checkbox checkbox-primary mt-0.5`, same link copy). Flagging as an open question for the planner (FSD placement, not visual).

### 3. TG-03 / TG-04 replacement states on `/telegram-register`

Both states **replace the entire form** (not shown alongside it) — the user has nothing to fill in if the token already expired or the email is already taken. Same card shell, same `card-body`, contents swapped for a status block:

```
<div className="card bg-base-200 shadow-xl w-full max-w-md">
  <div className="card-body items-center text-center gap-4">
    <h1 className="card-title text-2xl text-error">{/* TG-03: "Сессия истекла" / TG-04: "Email уже зарегистрирован" */}</h1>
    <p className="text-sm text-base-content/70">{/* body copy — see Copywriting Contract */}</p>
    <button className="btn btn-primary w-full">{/* restart or "Войти по почте" CTA */}</button>
  </div>
</div>
```

This centered-text variant of the card (`items-center text-center`) has no existing precedent in the 5 Phase-1/2 auth pages (all are left-aligned forms) — it is a deliberate, minimal new pattern for "dead-end, single-CTA" states, modeled on the existing `verify-email-page.tsx` `STATUS_CONFIG` pattern (which already centers its ✅/❌ status blocks the same way). Reuse that precedent's alignment convention rather than inventing a third one.

### 4. Post-login "Привязать Telegram" affordance (TG-04 tail end) — disabled, Phase-4 handoff

**Discretion resolved, same shape as Phase 2's disabled-button precedent:** TG-04 states the user is "offered «Привязать Telegram» after logging in" via email — but the actual linking round-trip (nonce → OIDC → `POST /auth/telegram/link`) is explicitly Phase 4 (LINK-01). Shipping a button with no working handler would repeat the exact mistake Phase 2 avoided. Resolution: add a **disabled** row to `profile-page.tsx`, following the same visual pattern already locked in Phase 2 §3 (VERIFY-03 resend row: `p-4 bg-base-100 rounded-2xl border border-base-content/10 flex items-center gap-4`), using `TelegramIcon` (`size-6`, `text-base-content/40` since disabled) + label "Привязать Telegram" + `title="Появится после запуска привязки Telegram в следующем обновлении"`. Only rendered when the user reaches `/profile` via the TG-04 conflict-then-email-login path — **not shown to every user unconditionally**, since most users won't have hit an email conflict. Detecting "arrived via TG-04" is a one-shot `sessionStorage` flag, same mechanism as `REGISTRATION_NOTICE_FLAG_KEY` (Phase 2) — planner should name it something like `TELEGRAM_LINK_HINT_FLAG_KEY` and follow the identical one-shot-listener pattern (`RegistrationNoticeListener` is the direct precedent to copy). **Flagging this discretion call explicitly for planner/user override, as Phase 2 did** — it affects the Phase 3/4 scope boundary.

- Card shell, `FormField`, button/spinner conventions, `alert-error` placement, footer link style — all identical to Phase 2, see `02-UI-SPEC.md` §Component Inventory #4 for the full locked list. Nothing in that list is modified by this phase.
