<objective>
Build the one genuinely-new piece of logic in this phase: forced navigation on terminal refresh failure (SESSION-04). Today `tryRefreshTokens()` calls `logout()` on failure — clearing tokens — but never navigates, so a user mid-session on a private page sees silently-broken data until their next full navigation trips `proxy.ts`. This plan closes that gap using RESEARCH.md's recommended Option A: dispatch `CustomEvent('auth:session-expired')` from the failure branches, and mount a small client listener in the `(web)` layout that calls `router.push()` reusing the existing `getSafeRedirect` utility, with a loop guard.

This is a complete, independently-verifiable slice: the only user-observable behavior change in the whole phase — "when your session truly expires, you land back on the login screen." Because `api-client.ts` is a plain module (not a React hook) it cannot call `useRouter()`; the event + mounted-listener indirection is the correct bridge (RESEARCH.md Anti-Patterns).

Purpose: Without this, a rejected refresh token leaves the user in a broken authenticated shell. This is the behavioral completion of the JWT session lifecycle.
Output: Event dispatch in `api-client.ts`, a new `SessionExpiredListener` component + test, wiring into `(web)/layout.tsx`, and a tokens-cleared + event-dispatched regression test.

Depends on Plan 02 because both edit `api-client.ts` / `api-client.test.ts`; this plan builds on the hardened static-import version.
</objective>

<threat_model>

## Trust Boundaries

| Boundary                                               | Description                                                                                                               |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| tryRefreshTokens() (plain module) → mounted React tree | The CustomEvent bridges a non-React module to the router; the event carries no attacker-influenced payload (empty detail) |
| current pathname → /login?from=... redirect target     | The `from` param is embedded into a navigation URL; an unsanitized path here is an open-redirect surface                  |

## STRIDE Threat Register

| Threat ID | Category                           | Component                                                          | Severity | Disposition | Mitigation Plan                                                                                                                                                                                                                                                                                                                     |
| --------- | ---------------------------------- | ------------------------------------------------------------------ | -------- | ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| T-1-02    | Tampering                          | forced-logout redirect `from` param                                | medium   | mitigate    | Reuse `getSafeRedirect()` (already validates path starts with `/`, rejects `//`, `/\\`, `javascript:`) to sanitize the current pathname before embedding it as the `from` param, then `encodeURIComponent` it — no new ad-hoc redirect sanitizer. The loop guard (skip when already on `/login`) also prevents a redirect loop DoS. |
| T-1-05    | Denial of Service (self-inflicted) | duplicated refresh after terminal failure                          | low      | mitigate    | This plan's forced navigation short-circuits the TanStack-Query second-attempt (Pitfall 4): once tokens are cleared and the event fires, a follow-up apiClient call hits the `if (!refreshToken)` branch and makes no second refresh network call — verified by Task 1's test                                                       |
| T-1-08    | Spoofing                           | forged window CustomEvent('auth:session-expired') from page script | low      | accept      | Only same-origin page scripts can dispatch window events; an attacker already running script in the page has full token access (T-1-03) so forging a logout event is strictly less severe. The event triggers only a client-side redirect, never a privileged mutation. Accepted.                                                   |
| T-1-03    | Information Disclosure             | tokens in localStorage                                             | high     | accept      | Accepted architectural tradeoff per PROJECT.md (bare-token backend contract, NextAuth rejected). Unchanged in this phase.                                                                                                                                                                                                           |
| T-1-SC    | Tampering                          | npm installs                                                       | n/a      | accept      | No package installs in this phase (RESEARCH.md: no new dependencies)                                                                                                                                                                                                                                                                |

</threat_model>
