<objective>
Harden and lock down the single-flight refresh mechanism that already exists in `api-client.ts`. Two pieces: (1) remove the unnecessary `await import('@/shared/lib/auth')` indirection at the top of `tryRefreshTokens()` (Pitfall 1 in RESEARCH.md) — replace with a static import so the dedup check is reached without an extra microtask hop; (2) add the missing regression tests that prove concurrent 401s collapse into exactly one refresh call (SESSION-02) and that a successful refresh swaps both tokens (SESSION-03).

This is a complete, independently-verifiable hardening slice: the single-flight lock becomes both tightened and test-locked in one unit. Do NOT rewrite the refresh logic — only the import mechanism changes; the `refreshPromise` singleton and `setTokens(access, refresh)` flow stay exactly as they are.

Purpose: Concurrent-request refresh is the highest-risk piece of the token lifecycle (refresh-token rotation means a race could invalidate in-flight requests). Locking it behind a deterministic test prevents silent regression when later phases add more authenticated call sites.
Output: A hardened `tryRefreshTokens()` (static import) and two new tests in `api-client.test.ts`.
</objective>

## Trust Boundaries

| Boundary                                          | Description                                                                                                                                  |
| ------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Browser tab → backend /auth/web/refresh           | The refresh token crosses here; because it rotates, a race or duplicate refresh could reuse a now-invalid token and drop concurrent requests |
| tryRefreshTokens() ↔ concurrent apiClient callers | The module-level refreshPromise is the coordination boundary that must collapse N concurrent 401s into one refresh                           |

| T-1-01    | Repudiation / Elevation of Privilege             | refresh-token rotation under concurrent 401s | high     | mitigate    | Single-flight `refreshPromise` singleton collapses concurrent refreshes into one call so the rotating refresh token is used exactly once; the new token pair is persisted atomically via `setTokens(access, refresh)` (SESSION-03). Task 1 tightens the dedup path (removes the pre-check async hop) and Task 2 locks the exactly-one-refresh + both-tokens-replaced guarantees behind a deterministic test. |
