# Phase 2 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Mission of this phase (per ROADMAP.md/PROJECT.md):** this is primarily an **audit-and-harden** phase, not new-UI-from-scratch. `register-page.tsx`, `login-page.tsx`, `verify-email-page.tsx`, `forgot-password-page.tsx`, `reset-password-page.tsx` already exist, work, and are covered by tests (PR #6, #9, #10, #20). This contract **locks their existing visual language** as the source of truth, flags the **copy drift** found between shipped code and `REQUIREMENTS.md`, and specifies the **one genuinely new surface**: the "shared auth screen" extension that exposes a Telegram entry point (full OIDC wiring lands in Phase 3 — TG-01..04).

## Design System

| Property          | Value                                                                                                                                                             |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Tool              | none — project does not use shadcn                                                                                                                                |

**Why no shadcn gate was run:** `components.json` is absent, but the project has a fully-established, CLAUDE.md-mandated design system (Tailwind 4 + DaisyUI 5, custom oklch `light`/`dark` themes in `src/app/globals.css`) already powering 5 tested auth pages. Introducing shadcn here would contradict the locked tech stack and create two parallel component systems inside the same auth flow. Skipped as inapplicable rather than asked.

## Spacing Scale

Declared values (multiples of 4 — matches Tailwind's default 4px base unit already in use):

| Token | Value | Usage (as observed in existing auth pages)                                                                          |
| ----- | ----- | ------------------------------------------------------------------------------------------------------------------- |
| xs    | 4px   | `gap-1`/`mt-0.5` — checkbox-to-label micro alignment                                                                |
| sm    | 8px   | `gap-2` — footer link stacks, icon+label gaps                                                                       |
| md    | 16px  | `gap-4` — form field stack, `mt-4` between form and footer/CTA — **default vertical rhythm inside every auth card** |
| lg    | 24px  | reserved for future section breaks inside the new auth-shell (divider + Telegram block)                             |
| xl    | 32px  | `page-container` desktop padding (`--page-padding` ≥768px), DaisyUI `card-body` internal padding                    |
| 2xl   | 48px  | not currently used in auth; do not introduce without reason                                                         |
| 3xl   | 64px  | not used                                                                                                            |

Exceptions: `min-h-[60vh]` wrapper for vertical centering of the auth card is a layout primitive, not a spacing token — keep as-is (used identically across all 5 pages).

Card width: fixed `max-w-md` (28rem/448px) centered, full-width on mobile via `page-container` padding. Do not change per-breakpoint — this is the locked pattern across all 5 pages.

## Typography

| Role                                            | Size                                       | Weight         | Line Height |
| ----------------------------------------------- | ------------------------------------------ | -------------- | ----------- |
| Micro (field error / help text)                 | 12px (`text-xs`)                           | 400 (regular)  | 1.5         |
| Body (inputs, labels, footer links, alert text) | 14px (`text-sm`)                           | 400 (regular)  | 1.5         |
| Button / interactive label                      | 16px (`text-base`, DaisyUI `.btn` default) | 600 (semibold) | 1.2         |
| Heading (`card-title`)                          | 24px (`text-2xl`)                          | 600 (semibold) | 1.2         |

Exactly 4 sizes (12/14/16/24), exactly 2 weights (400/600) — matches existing rendered output of `.card-title`, `.btn`, `.input`, `.alert`, `FormField` label/error across all 5 pages. Do not introduce a 3rd weight (e.g. bold 700) anywhere in this phase's new work.

`gradient-text` utility (`bg-linear-to-r from-primary to-info text-transparent bg-clip-text`, defined in `globals.css`) is the **only** heading treatment used across the 5 pages — reuse verbatim for any new heading, do not invent a new heading style.

## Component Inventory — New Work This Phase

### 1. Auth-shell Telegram extension (the "shared auth screen" from the Phase 2 goal)

Re-reads ROADMAP Phase 2 success criterion 5 literally: _"User can log in with existing email/password from the auth screen (which also offers 'Войти через Telegram' / 'Регистрация')"_ — the **auth screen is the existing login-page card**, extended, not a new standalone chooser page. Minimal-diff interpretation, consistent with "audit-and-harden, not new UI from scratch."

Layout inside `login-page.tsx`'s existing `card-body`, appended **after** the `Войти` submit button and **before** the existing footer links block:

```
[existing form: Email input, Пароль input, server error alert, Войти button]
[NEW] <div className="divider text-sm text-base-content/50">или</div>
[NEW] <button className="btn btn-outline btn-primary w-full gap-2" disabled>
        <TelegramIcon className="size-5" /> Войти через Telegram
      </button>
[existing footer: Нет аккаунта? / Забыли пароль?]
```

**Discretion resolved — Telegram button state in Phase 2:** rendered **disabled** (DaisyUI `btn-disabled`/native `disabled`), not wired to any click handler or route. Full nonce→OIDC→login wiring is explicitly Phase 3 (TG-01). Shipping an enabled button with no working handler in Phase 2 would be a dead-end click — worse UX than an honest disabled state. Satisfies "offers" (visually present) from the success criterion without overstating readiness. Add a small `title="Появится после запуска Telegram-входа"` tooltip attribute for discoverability. **If this discretion call is wrong, the planner/user should override before planning** — flagging explicitly since it affects Phase 2 scope boundary with Phase 3.

New icon component required: `src/shared/ui/icons/telegram-icon.tsx`, same shape/prop contract as `water-drop.tsx` (`size?: number`, `className?: string`, single outline SVG path, `viewBox="0 0 24 24"`, paper-plane glyph, `currentColor`). Export via `src/shared/ui/icons/index.ts`.

### 2. REG-03 post-registration notice

Not rendered on `register-page.tsx` itself (user is redirected immediately via `getSafeRedirect`). Must surface on the landing page after redirect. Recommended pattern (visual contract only — implementation left to planner): a one-shot `alert alert-info` banner, dismissible, shown on next page load using the same `sessionStorage` one-shot pattern already established for `registrationToken` (`shared/lib`) — do not introduce a toast library (`react-toastify` is an unused dependency; adding it here is out of scope for this phase, a plain `alert-info` banner matches existing conventions in `forgot-password-page.tsx`/`reset-password-page.tsx`).

### 3. VERIFY-03 resend-verification affordance

`resendVerification(accessToken)` already exists in `features/auth/api/auth-api.ts` but has **no UI entry point** anywhere. Recommended placement: a new row in `profile-page.tsx`, following the exact visual pattern of the existing `Изменить почту` / `Сменить пароль` rows (`p-4 bg-base-100 rounded-2xl border border-base-content/10 flex items-center gap-4`), using `EnvelopeIcon` (already imported there) or a checkmark variant, label «Подтвердить почту» → «Отправить письмо повторно». **No conditional gating on verification status is required or available** — `TUser` (`shared/model/t-user.ts`) has no `emailVerified`/`is_verified` field. Do not block this action on a verification flag; make it an always-available idempotent action (matches VERIFY-03's wording — no unverified-state banner is required by the requirement). Flagging the missing `TUser` field as an open question for planner/backend coordination, not something to solve visually.

### 4. Existing pattern — locked, no changes

- Card shell: `card bg-base-200 shadow-xl w-full max-w-md` + `card-body`, centered via `flex items-center justify-center min-h-[60vh]` inside `PageContainer` (default `bg-base-300`).
- Form fields: `FormField` (`shared/ui/form-field`) wrapping DaisyUI `floating-label` + `input input-bordered w-full`, `input-error` modifier + `text-error text-xs mt-1` error line.
- Buttons: `btn btn-primary w-full`, loading state = `<span className="loading loading-spinner loading-sm" />` replacing label while `isSubmitting`.
- Server-level errors: `alert alert-error text-sm` block above/below the submit button.
- Footer links: `text-center text-sm mt-4` + `link link-primary`.
- `verify-email-page.tsx` uses emoji glyphs (✅/❌ at `text-5xl`) instead of heroicons for its success/error states — an existing inconsistency vs. the rest of the app's icon system. **Non-blocking observation, not in scope to fix this phase** (REQUIREMENTS doesn't ask for it); noting for `gsd-ui-checker` awareness so it isn't mistaken for new drift.
